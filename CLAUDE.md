# SAR Review — контекст проекта для Claude Code

## Что это такое

Self-hosted веб-сервис для поиска людей/снаряжения на видео и фото с дрона.
Разработан **во время реальной поисково-спасательной операции** МЧС Кыргызстана —
поиск пропавших альпинистов в Алайском районе, у пика Корумду. Не учебный
проект и не демо — им реально пользуются в поле, поэтому:

- **Регрессии стоят дорого.** Если что-то ломается — это не "поправим на
  следующем спринте", а прямо сейчас у людей на месте операции не работает
  инструмент, которым они пытаются найти пропавших.
- **Каждое серьёзное изменение в этом проекте до сих пор проверялось
  реальными тестами**, а не "должно работать" на глаз — Flask test client
  для роутов, прямые вызовы функций для детектора/группировки, `node --check`
  для встроенного JS, синтетические сценарии, воспроизводящие точную
  ситуацию бага. Продолжай эту практику — она уже не раз ловила баги (включая
  баги в самих тестах, которые нужно было переисследовать).
- Инструмент не заменяет стандартные протоколы поиска — это приоритизация
  внимания человека, а не замена наземных групп/повторных облётов.

## Архитектура целиком

```
watch_dir (корень проекта, там же и лежат sar_*.py)
  ├── видео/фото с дрона          <- кладутся ПРЯМО в корень, подпапки НЕ сканируются
  ├── sar_config.json             <- реальный конфиг (НЕ в архиве обновлений, см. ниже)
  ├── sar_config.example.json     <- шаблон, можно перезаписывать
  └── sar_data/                   <- всё служебное, создаётся автоматически
        ├── sar_data.db           <- SQLite, WAL-режим, общая точка синхронизации
        ├── secret.key            <- Flask secret key, персистентный между рестартами
        └── reports/<report_id>/  <- report.html, detections.json, crops/, frames/
```

**Два независимых процесса, общаются ТОЛЬКО через sar_data.db (SQLite) и
файловую систему — никаких прямых связей друг с другом:**

- **`sar_worker.py`** — вся обработка. Следит за папкой (`watcher_loop`,
  без рекурсии), ставит новые файлы в очередь, запускает
  `sar_video_review.py`/`sar_photo_review.py` отдельным процессом на
  каждый файл, стримит его stdout в таблицу `logs`, парсит прогресс,
  управляет жизненным циклом дочерних процессов (graceful shutdown,
  registry активных процессов). **Не знает о Flask вообще.**
- **`sar_server.py`** — чистый Flask-слой. Только читает БД и файлы на
  диске, ничего не обрабатывает и не запускает сам. Логин (общий пароль +
  любое имя), список файлов, отдача готовых отчётов, ручной плеер, API.

**Почему так разделено:** перезапуск/обновление `sar_server.py` НЕ прерывает
текущую обработку видео — она продолжается в `sar_worker.py` независимо.
Обновление `sar_worker.py` не теряет очередь и готовые результаты, но то
видео, что как раз обрабатывалось в момент его остановки, пересчитается с
нуля при перезапуске — checkpoint/resume внутри детектора не реализован.

- **`sar_telegram_bot.py`** — третий независимый процесс. Выдаёт персональные
  ссылки входа, принимает заявки на доступ, показывает changelog и справку.
  Как и остальные, общается с платформой ТОЛЬКО через БД. **Общий пароль в
  чат не отправляется никогда** — только персональная ссылка, и она уходит
  отдельным самоудаляющимся сообщением (5 секунд).
- **`sar_health.py`** — сбор метрик в формате Prometheus (`/metrics`):
  счётчики и гистограмма латентности HTTP по эндпоинтам, возраст резервной
  копии, свободное место, живость процессов через `service_heartbeat`.
- **`sar_alerts.py`** — правила тревог поверх состояния БД.
- **`sar_backup.py`** — резервные копии БД. **Путь к папке копий считается
  ровно в одном месте — `sar_common.backups_dir()`.** Раньше он вычислялся в
  трёх местах, два из которых были неверны, и мониторинг годами смотрел не
  туда (см. грабли).
- **`sar_loadtest.py`**, **`sar_dataset_export.py`**, **`sar_extract_finds.py`** —
  вспомогательные CLI: нагрузочное тестирование, выгрузка датасета, извлечение
  находок.
- **`monitoring/`** — docker-compose с Prometheus и Grafana, дашборд и
  источник данных заведены файлами (`provisioning`), uid `sar-prometheus`.

### Остальные файлы

**`sar_data/` НЕ ОБЯЗАН лежать внутри `watch_dir`.** Начиная с 13.09.2026
путь настраивается (`server.data_dir`), умолчание прежнее. Сделано ради
переезда материала в облако: материал — это десятки крупных файлов, читаемых
подряд и по одному разу, а служебное — сотни тысяч мелких файлов отчётов,
которым нужен локальный SSD. В одной папке их держать нельзя.

- **`sar_common.py`** — общий код между сервером и воркером: конфиг,
  схема БД (`init_db`, идемпотентна, безопасно вызывать из обоих процессов
  в любом порядке запуска), сканирование папки, генерация `report_id`.
  Без зависимости от Flask.
- **`sar_video_review.py`** — детектор для видео. Тайлинг кадра (overlap
  между тайлами), инференс через `ultralytics` (YOLO-World — открытый
  словарь классов без дообучения, либо своя `custom`-модель), плюс
  отдельный HSV-детектор цветовых аномалий (для снаряжения/одежды, которое
  object detection на мелком масштабе часто пропускает). Группировка
  детекций в "сцены" (онлайн-трекер по классу+источнику+близости
  во времени/пространстве, макс. разрыв по кадрам и допустимый снос бокса
  настраиваются). Парсинг SRT-телеметрии для GPS по таймкоду. Генерирует
  самодостаточный статический `report.html` (сетка карточек сцен, клик →
  все кадры сцены, клик по кадру → полноэкранный просмотр с зумом
  мышью/пальцем и переключаемым оверлеем рамок). Поддерживает CLI напрямую
  (без сервера) и вызов через `sar_config.json`.
- **`sar_photo_review.py`** — тот же детектор, применённый к одиночному
  фото (переиспользует функции из `sar_video_review.py`).
- **`sar_batch.py`** — отдельный CLI для пакетной обработки папки БЕЗ
  веб-сервиса (очередь на одной машине, resume после сбоя, флаг `--workers`).

## Схема БД (SQLite, WAL)

- **`reports`** — report_id (PK, = имя_файла + дата_создания_файла +
  короткий хэш пути), rel_path, abs_path, kind (video/photo), status
  (queued/processing/done/error), progress_pct, total_frames, fps,
  duration_sec, error, out_dir, file_ctime, phase, created_at, updated_at
- **`logs`** — построчный лог консоли обработки на report_id
- **`watch_segments`** — report_id, viewer_name, start_sec, end_sec, ts.
  **Общая таблица для двух разных источников** "человек это посмотрел":
  пинг при открытии сцены в автоматическом режиме, и реальные проигранные
  диапазоны в ручном плеере (`timeupdate`-based). Оба пишутся сюда же —
  единая метрика покрытия "просмотрено ли это человеком", неважно каким
  способом.
- **`presence`** — viewer_name (PK), last_seen. Heartbeat раз в 15с с
  клиента, "онлайн" = уникальные имена с last_seen не старше 40с.
- **`manual_observations`** — ручные пометки в плеере: report_id,
  viewer_name, timestamp_sec, bbox (JSON, нормализовано 0..1 от размера
  кадра), label, note, lat, lon (автоматически подтягивается из SRT по
  timestamp_sec), created_at.

- **`operations`** + **`operation_materials`** — операция как единица работы;
  материалы привязываются к операции через join-таблицу. Платформа рассчитана
  на **несколько одновременных операций**. Папка операции помечается файлом
  `.sar_operation`.
- **`detection_priorities`** — триаж находок (приоритет/статус). **Колонка
  времени называется `set_at`, а не `updated_at`** — на этом уже обожглись.
- **`detection_comments`** — обсуждение находок.
- **`telegram_access_requests`** — заявки на доступ из бота.
- **`service_heartbeat`** — живость процессов для мониторинга. Долгие операции
  (кодирование прокси-копии) обязаны обновлять heartbeat в цикле, иначе
  мониторинг объявит воркер мёртвым во время нормальной работы.
- **`alert_state`** — состояние тревог, чтобы не слать их повторно.

## Ключевые фичи (уже реализовано)

1. Мультикласс-детекция (YOLO-World без дообучения ИЛИ своя модель) +
   цветовые аномалии как отдельный, дополняющий сигнал.
2. Группировка тысяч сырых детекций в компактные "сцены" — иначе страница
   с отчётом становится нерабочей на масштабе.
3. `report.html` — полностью самодостаточный файл, открывается и без
   сервера (хук трекинга просмотров — no-op, если сервер не передал
   `tracking_report_id`/`tracking_api_base`).
4. Ручной плеер (`/report/<id>/player/`): рисование боксов мышью (видео
   ставится на паузу на момент начала разметки, чтобы не "уехал" таймкод),
   GPS автоматически по SRT, полоса покрытия по факту реального
   проигрывания, **опциональный оверлей рамок модели** (чекбокс, легенда,
   отдельная цветовая схема от ручных пометок).
5. **Живой предпросмотр AI-рамок во время обработки** —
   `flush_partial_detections()` в `sar_video_review.py` периодически
   (каждые 50 обработанных кадров) атомарно (temp-файл + `os.replace`)
   дописывает текущий список найденного в `detections.json`, не дожидаясь
   конца обработки. Плеер доступен и во время обработки (не только после
   `done`), с баннером и настраиваемым авто-опросом
   (`server.player_ai_poll_interval_sec` в конфиге, сервер сам зажимает
   минимум 5 секунд — конфиг не может заставить клиента опрашивать чаще).
6. Экономия диска: `full_frame_save_mode: "representative"` — оставляет
   только первый/пиковый/последний полный кадр на сцену вместо всех.
7. Восстановление после сбоя: `recover_stale_processing_reports()` в
   `sar_worker.py` при старте возвращает в очередь всё, что зависло в
   `processing` с прошлого запуска.
8. Список файлов: сортировка (тип/имя/дата создания), живая полоса
   покрытия, индикатор "N онлайн" (простая зелёная точка, без анимации).

9. **Операции** — материалы группируются по операциям, главный экран после
   входа — список операций, а не плоский список файлов. Любая ссылка «к списку
   файлов» должна вести на экран операции.
10. **Роли** (`ROLE_*` в `sar_common.py`): участник, модератор обсуждений,
    администратор, без права комментировать. **Права никогда не выдаются по
    догадке о личности человека** — только явным действием.
11. **Находки**: превью на странице операции с окном предпросмотра по наведению
    (зум колесом и пальцами, панорамирование ЛКМ), фильтр по статусу, включая
    «показать все» и отклонённые.
12. **Прокси-копии видео** — воркер фоном делает облегчённую копию (CRF 26,
    `-movflags +faststart`) для плеера; оригинал отдаётся по `?original=1`.
    На материале операции 23,2 ГБ → 2,7 ГБ. Публикация атомарна через
    `os.replace`.
13. **Кеш `/api/tree`** — TTL, single-flight, отдача устаревшего значения с
    фоновым обновлением, ожидание на холодном старте. Медиана улучшилась в 42
    раза. Ключ кеша обязан включать `watch_dir` и путь к БД, иначе тесты с
    временными каталогами видят чужие данные.
14. **Метрики и мониторинг** — Prometheus + Grafana, окно по умолчанию 5 минут.
15. **Телеграм-бот** — персональные ссылки, заявки на доступ, автоподтверждение
    на срок, changelog.
16. **Страница находки** (`/finding/<id>/`) — крупный кадр, вся карточка,
    обсуждение теми же эндпоинтами, что и в плеере. **Постоянная ссылка на
    находку идёт через бота** (`t.me/<bot>?start=finding_<id>`), а не через
    адрес платформы: адрес туннеля меняется при каждом перезапуске, и прямая
    ссылка протухает молча — открывается чужая страница или ничего.
17. **Облачные хранилища** (`sar_cloud.py`, `sar_staging.py`, `sar_fetch.py`).
    Материал может лежать в Google Диске или Яндекс.Диске, а локально
    остаются только отчёты и лёгкие копии. Устройство:
    - **`sar_cloud`** — провайдеры. Листинг, скачивание с докачкой, чтение
      по частям. Только стандартная библиотека.
    - **`sar_staging`** — временная папка с жёстким потолком и вытеснением
      по давности. Закреплённые (в обработке) не вытесняются никогда.
      **Освободить нечем — скачивание НЕ начинается**, бросается
      `NoRoomError`. Переполнить диск, где лежит база, нельзя.
    - **`sar_fetch`** — ЕДИНСТВЕННАЯ дверь к байтам (`ensure_local`). Держит
      одновременность, место, суточный лимит. Три двери означали бы три
      набора ограничителей, которые разойдутся.

    **Токен вводится вручную, OAuth с перенаправлением НЕ используется:**
    ему нужен постоянный адрес возврата, а у платформы его нет — туннель
    меняет имя при каждом перезапуске. Токены наружу не отдаются никогда
    (`cloud_accounts_public()` — отдельная функция, а не фильтр на месте
    использования: фильтр, который надо не забыть, забудут).

    **Совпадение материала ищется по `rel_path`**, поэтому перенос папки в
    облако С СОХРАНЕНИЕМ СТРУКТУРЫ подхватывает существующие записи вместе
    с пометками и обсуждениями, а не плодит дубли.
18. **Админка (`/admin`) и настройки на ходу.** Таблица `settings` в базе,
    реестр `SETTINGS_SCHEMA` в `sar_common` — одно место, где описано имя,
    тип, умолчание, границы и человеческое пояснение каждого параметра.
    Форма строится из реестра, второго списка полей во фронтенде нет (есть
    тест-страж). Значения **зажимаются** по границам, а не отвергаются, и
    ответ показывает то, что РЕАЛЬНО сохранено: ввели 50 — увидели 4.
    **Почему в базе, а не в конфиге:** меняет сервер, применяет воркер, а
    они общаются только через базу — запись в `sar_config.json` до воркера
    не доехала бы до перезапуска. Воркер перечитывает настройки каждый
    проход. Ключ `auto_process` переносится из конфига в базу один раз
    (`seed_settings_from_config`), иначе установка с `false` молча начала бы
    обрабатывать всё подряд.
19. **Пути вычисляются, а не хранятся** (`sar_common.material_path`,
    `report_dir`). Столбцы `abs_path`/`out_dir` остаются в схеме ради внешних
    разовых скриптов, но платформа их НЕ ЧИТАЕТ. База перестала быть
    привязанной к машине, букве диска и ОС — это общий фундамент и для
    облака, и для переезда на VPS. Есть тест-страж.
20. **Выгрузка находок в KML и GPX** (`/api/operations/<id>/findings.kml|gpx`) —
    координатор работает в своей карте или в навигаторе, а не в платформе.
    **В выгрузке РАЗДЕЛЕНЫ два разных вида точек**: позиция дрона из телеметрии
    и вероятная точка объекта на земле (расчёт `estimate_ground_point`). На
    материале операции они расходятся на 653 метра — подписать одно другим
    значит увести группу в соседнее ущелье. В KML это разные папки с разными
    значками, в GPX (папок нет) — пометка `[дрон]` прямо в имени точки плюс
    поле `<type>`. Точка без пары координат пропускается, а не роняет
    выгрузку целиком.
21. **Карта находок** — вкладка «Карта» на странице операции (17.09.2026).
    Leaflet лежит СВОЙ, в `static/leaflet/` — не с CDN: платформа обязана
    работать в поле без интернета. Подложка (тайлы OSM) без сети не придёт,
    но точки, треки и разметка останутся видны.

    **Карту не делали до сих пор не из-за карты, а из-за качества
    координат**, и это осталось главным требованием к ней:
    - «точка объекта» и «позиция дрона» — РАЗНЫЕ значки, как в выгрузке KML;
    - между ними рисуется линия: разнос видно глазом, а не читаешь в подписи;
    - **сколько находок на карту НЕ попало — написано прямо под ней.**
      Карта, молча скрывающая половину пометок, хуже отсутствия карты: по
      ней делают вывод, что искать больше негде. На боевых данных это
      8 с точкой объекта, 7 только с дроном, **17 без координат вовсе**.

    Данные берутся из `_findings_for_export()` — той же сборки, что KML и
    GPX. Второй расчёт «объект или дрон» означал бы два расходящихся ответа
    на один вопрос.

    **Отметка на карте** (`map_marks`) — третий вид точки: не наблюдение в
    кадре, а место на земле («сюда идёт группа», «это ущелье не облетали»,
    «свидетель указал сюда»). ОТДЕЛЬНАЯ таблица, а не строка в
    `manual_observations`: там `report_id NOT NULL`, и разрешив пустой, мы
    обязали бы каждую выборку пометок, каждый подсчёт покрытия и каждую
    страницу находки помнить про строки без материала. Чужую отметку может
    убрать только модератор — поставленная координатором это указание.

    **Треки дрона** (`/api/operations/<id>/tracks`) — необязательный слой,
    географическая версия покрытия: по находкам видно, где смотрели, по
    трекам — куда вообще летали. На боевых данных 18 треков из 114 видео,
    у остальных телеметрии нет, и это число тоже показано.

    **Разбор делает ВОРКЕР, не веб-слой** (`ensure_telemetry_tracks`,
    таблица `telemetry_tracks`). Сначала было сделано наоборот — сервер
    разбирал SRT по запросу, — и это неверно дважды: сервер по устройству
    проекта только читает, а на деле каждый холодный запрос разбирал 114
    файлов (**2,9 с**) и складывал результат в кеш, живущий в памяти
    процесса и умирающий при перезапуске. После переноса **0,03 с**, и
    разницы между холодным и повторным запросом нет вовсе.

    Три вещи, которые легко сломать обратно:
    - **Пустой `points` = «разобрали, телеметрии нет»**, а НЕ «ещё не
      разбирали». Без этой отметки 62 видео без SRT разбирались бы заново
      каждый проход, вечно. На карте это тоже разные подписи: первое не
      изменится никогда, второе пройдёт само.
    - **`source_mtime`** — чтобы перечитать, если человек дозалил
      телеметрию, и не перечитывать, если нет.
    - **Прореживание — РОВНОЕ распределение по индексам, а не «каждая
      N-я»**, и ровно `TRACK_MAX_POINTS` точек. Деление нацело давало 419
      при потолке 400 (потолок протекал), округление вверх теряло половину
      точек на треках чуть длиннее потолка (486 → 243). Первая и последняя
      точки сохраняются всегда: обрубив конец, мы показали бы, что дрон не
      долетел туда, куда долетел.

    `telemetry_tracks` НЕ в `CRITICAL_TABLES` бэкапа осознанно: это разбор,
    а не работа человека — потеряется, воркер соберёт заново.

    **Лицензии.** Leaflet BSD-2 (совместим с MIT), текст лежит рядом.
    Атрибуция OpenStreetMap обязательна по ODbL и убирать её нельзя. Всё
    стороннее перечислено в `THIRD-PARTY.md` — там же предупреждение про
    ffmpeg на случай портативной сборки.

22. **Отчёт по операции** — вкладка «Отчёт» (18.09.2026). До этого была
    заглушка «в работе».

    **Главное в отчёте — не найденное, а НЕ ПРОСМОТРЕННОЕ.** Отчёт,
    показывающий только находки, льстит: он отвечает на вопрос «что мы
    нашли», тогда как решение принимается по вопросу «куда ещё не
    смотрели». На боевых данных это **80 видео из 114, которые не открывал
    ни один человек** — при заголовке, обещавшем 86% покрытия.

    Разделы: объём, покрытие (непросмотренное — первым и подсвеченным),
    второй проход, находки по статусам триажа, кто работал, таблицы
    покрытия по видео и по фото, и обязательный раздел **«чего этот отчёт
    не показывает»**.

    **Таблицы**: видео — файл, папка, процент просмотренного, число
    просмотров, сколько человек, сколько находок; фото — отдельной
    таблицей. Сортировка по любому столбцу, фильтр по имени, всё в
    браузере (206 строк — несколько килобайт).

    **Период фильтрует РАБОТУ, а не дату съёмки.** «Отчёт за 15 августа» —
    это что сделали 15-го: какие отрезки посмотрели, какие пометки
    поставили. Конец периода включает указанный день ЦЕЛИКОМ.

    **Обезличивание** (`?anon=1`): «волонтёр А», «волонтёр Б»… по убыванию
    вклада — структурный вывод («двое сделали больше половины») сохраняется,
    имена нет. Псевдоним раздаётся при СБОРКЕ данных, а не при отрисовке, и
    покрывает все источники имён (просмотры, пометки, отметки на карте):
    фильтр, который надо не забыть применить в каждом месте, однажды
    забудут — тот же урок, что с токенами облака.

    Три вещи, которые легко сломать обратно:
    - **Просмотры считаются ПО КАЖДОМУ ЧЕЛОВЕКУ отдельно** и складываются.
      По общей ленте времени двое, смотревшие одновременно, слипались в
      один просмотр — выходило «просмотров 6, людей 8». Разрыв больше
      `SESSION_GAP_SEC` = новый заход; по отрезкам считать нельзя вовсе
      (один человек за заход даёт их сотни).
    - **Неизвестная длительность даёт `null`, а не 0%.** Ноль читается как
      «не смотрели», хотя смотреть могли — просто посчитать не из чего.
    - **Про фотографии платформа НЕ ЗНАЕТ, смотрели их или нет.** Отрезки
      пишет только плеер видео и пинг открытия сцены; у снимка ни того, ни
      другого. Отдаётся признак `photos_tracked`, а не выдуманный ноль:
      «просмотрено 0 из 92» было бы ложью. **Это реальный пробел
      платформы**, а не отчёта.

## ВАЖНЫЕ грабли, на которые уже наступали — не наступи снова

- **Windows + кодировка**: `subprocess.Popen` обязан получать
  `encoding="utf-8", errors="replace"`, а дочерний процесс — переменную
  окружения `PYTHONIOENCODING=utf-8`. Без этого — кракозябры на русском
  тексте в логах (ANSI cp1251 vs OEM cp866 vs UTF-8 конфликт на Windows).
- **Windows + буферизация**: дочерний Python-процесс обязан запускаться
  с флагом `-u` (плюс `PYTHONUNBUFFERED=1` в env). Без этого `print()` в
  дочернем процессе буферизуется блоками, когда stdout — не терминал, а
  пайп: вывод "зависает" и появляется весь разом только при завершении
  процесса (выглядит как реальное зависание, хотя работа идёт).
- **SVG-оверлей поверх `<video>`**: обязательно `pointer-events:none` по
  умолчанию, включать `auto` только в момент реального рисования — иначе
  оверлей перехватывает клики по нативным кнопкам плеера (play/пауза/
  перемотка становятся нежмущимися).
- **Никогда не вкладывай `<a>` в `<a>`** в генерируемом HTML — невалидно,
  браузер разбирает непредсказуемо, ссылка может не работать. Уже был
  такой баг с "▶ плеер" в списке файлов.
- **Статус `processing`, зависший навсегда**: если процесс, следящий за
  выводом детектора, был перезапущен/убит до того, как записал финальный
  статус — запись в БД так и останется на `processing`, хотя реальная
  обработка на диске уже полностью завершена (`report.html`/`detections.json`
  готовы). `recover_stale_processing_reports()` чинит это при рестарте
  **воркера**; для уже осиротевших процессов от совсем старых версий кода
  есть отдельный разовый скрипт `fix_stuck_report_status.py` — чинит
  статус по факту наличия полных файлов на диске, без пересчёта.
- **Порядок координат в `GPS(a,b,c)` без подписей lat/lon** — не
  стандартизован между прошивками DJI. Никогда не угадывать порядок —
  настраивается через `srt_gps_tuple_order` ("lat_lon"/"lon_lat"),
  неправильная догадка тут хуже, чем отсутствие координаты вообще.
- **Проверяй импорты после любого урезания/рефакторинга файла.** При
  разделении `sar_server.py`/`sar_worker.py` один раз забыли `import time`,
  используемый только в двух функциях веб-слоя (`get_online_count`,
  `api_heartbeat`) — сломался счётчик "онлайн", тихо (JS проглатывал
  ошибку через пустой `catch`). Есть готовый паттерн проверки: AST-обход
  файла + grep на `name.метод(` для имён, которые могли остаться
  "осиротевшими" — см. как это делалось при диагностике этого бага.
- **CPU-инференс через `ultralytics`/`torch` сам растягивается на все
  ядра машины** по умолчанию — если когда-нибудь включать `workers > 1` в
  конфиге, без явного `torch.set_num_threads()`/`OMP_NUM_THREADS` на
  процесс несколько воркеров будут драться за одни и те же ядра, а не
  честно распараллеливаться. Сейчас **не реализовано**, `workers: 1` —
  осознанный выбор, а не заглушка.
- **`sar_config.json` — реальный конфиг пользователя, никогда не должен
  попадать в архив/репозиторий обновлений.** В комплекте только
  `sar_config.example.json` (шаблон). Раньше был баг: конфиг лежал прямо
  в архиве, и каждая распаковка "с заменой" тихо затирала пароль обратно
  на дефолтный `change_me`.

### Молчаливые отказы — главная категория багов в этом проекте

Все перечисленные ниже баги **пережили боевое применение незамеченными** и
нашлись только тогда, когда появилось время посмотреть на данные. Ни один из
них не выглядел как ошибка: платформа не падала, кнопки нажимались. Поэтому:

- **`except Exception: pass` и пустой `catch` — запрещены по умолчанию.**
  Если исключение действительно можно проглотить, рядом должен быть комментарий
  почему. Отметки триажа не показывались из-за связки «неверное имя колонки в
  `ORDER BY`» + «проглоченное исключение» — 47 отметок не видел никто.
- **`setAttribute` принимает строку `"NaN"` молча.** Функция `overlaySize()`
  возвращала `{w, h}`, а отрисовка читала `rect.width` → боксы не рисовались
  вообще, без единой ошибки в консоли. При расхождении имён полей между
  функцией и её потребителем ничего не сломается заметно.
- **Порядок декораторов Flask.** Вставка нового `before_request`-хука **между**
  `@app.before_request` и `def require_login()` увела декоратор на хук метрик,
  а `require_login` осталась незарегистрированной — платформа открылась без
  пароля. Поймали существующие тесты; добавлен отдельный тест-страж.
- **Один и тот же путь, посчитанный в нескольких местах, разойдётся.** Путь к
  папке резервных копий считался трижды, два раза неверно; мониторинг рапортовал
  о свежести копий, которых там не было.
- **Метрика, которую забыли внедрить везде.** Heartbeat присутствия стоял на 3
  страницах из 6, и на главной после входа его не было — счётчик «онлайн»
  занижал число работающих людей. Такие вещи внедрять единой точкой, а не
  копированием по шаблонам.
- **«Где файл?» и «настоящий ли это материал?» нельзя спрашивать у ДИСКА —
  уже ЧЕТЫРЕЖДЫ.** Облачного материала на диске нет ПО ОПРЕДЕЛЕНИЮ, и
  каждая такая проверка отвергает его МОЛЧА, при готовом результате рядом:
  1. отдача видео возвращала 404 при готовой лёгкой копии;
  2. `find_material_file` не находила облачное;
  3. отдача превью материала (17.09.2026) отвергала все 148 готовых JPEG —
     сверяла имя со `scan_all_materials(watch_dir)`; чинится сверкой с
     `reports` по точному `rel_path` (защита от подстановки пути не слабее);
  4. превью НАХОДКИ (18.09.2026) резалось только из оригинала
     (`material_path` + `os.path.exists`), поэтому пометка на облачном видео
     оставалась пустым квадратом навсегда. Чинится порядком «оригинал →
     лёгкая копия»: копия это тот же материал с теми же таймкодами.

  Общее правило: источник материала ищется через `find_material_file`
  (наблюдаемая папка + временная), а если и там нет — годится лёгкая копия.
  На каждый случай стоит тест-страж.
- **Файл, который не обрабатывается, забирает единственный слот НАВСЕГДА.**
  Копий делается одна за проход. Файл без копии выбирается следующим
  проходом снова — и если собрать её невозможно, очередь из восьмидесяти
  файлов встаёт за одним. 17.09.2026 так и вышло: в Google Диске нашёлся
  MP4, залитый не до конца (отдаётся 593 МБ, внутри заявлено 3,44 ГБ —
  индекс, который DJI пишет в конец, до хранилища не доехал). Сверка
  размера не спасает и не виновата: скачано ровно столько, сколько облако
  обещало. Теперь неудача сборки отступает с паузой, а после исчерпания
  попыток причина пишется в `reports.error` и видна человеку.
- **Пустой вектор в PromQL даёт пустую панель, а не ноль.** Панель ошибок
  молчала не потому, что ошибок нет.

### Грабли подготовки к облаку (13.09.2026)

Материал операции исторически загружается в Google Диск и Яндекс.Диск.
Задача: держать локально только служебное, до 10 ГБ. Разбор показал, что
архитектура к этому приспособлена лучше ожидаемого — прокси-копии уже
реализуют принцип «тяжёлое отдельно, работаем с лёгким», — но нашлись мины:

- **`cap.read()` возвращает `False` и в конце файла, и при обрыве чтения.**
  Различить нельзя. Раньше в обоих случаях писался нормальный на вид отчёт
  по половине видео: статус «готово», сцены есть, человек идёт дальше, а
  вторую половину не смотрел никто. Теперь недобор кадров сверх допуска —
  `IncompleteReadError`, отчёт не пишется. Допуск 1% или 2 кадра (у части
  контейнеров счётчик приблизительный; на DJI MP4 он точен — сверено с
  ffprobe). **Нет счётчика — молчим осознанно:** выдуманная тревога учит
  людей игнорировать настоящие.
- **Превью и длительность считались для КАЖДОГО файла на КАЖДОМ проходе**
  (раз в 15 с), а признаком «надо» было отсутствие файла превью. Сорвалась
  генерация — повтор навсегда, 240 попыток в час. На локальном диске
  безобидно, в облаке каждая попытка станет скачиванием. Добавлен backoff
  с потолком и отказом после 8 попыток (`_may_try`/`_note_failure` в
  `sar_worker.py`), состояние в памяти процесса — перезапуск воркера это
  осмысленный сигнал «попробовать заново».
- **Порядок проверок в отдаче видео.** `if not os.path.exists(abs_path)`
  стояло ДО подстановки прокси — то есть при материале в облаке плеер вернул
  бы 404, хотя прокси лежит рядом и готов. ИСПРАВЛЕНО: оригинал обязателен
  только при `?original=1`, и отказ тогда подсказывает снять галочку.
- **Первый проход по подключённой папке — лавина.** Превью и длительность
  считались для КАЖДОГО файла на КАЖДОМ проходе. Добавлен бюджет
  `MATERIAL_TOUCHES_PER_PASS = 3`, и считает он РЕАЛЬНЫЕ чтения файла, а не
  вызовы функций: дешёвая проверка «превью уже есть» бюджет не тратит, иначе
  за проход осматривались бы три файла вместо всей папки.
- **Клиент Google Диска в реализации НЕ участвует.** Совет «перенести его
  кеш» относился к отвергнутому варианту с монтированием облака как диска;
  к реализованной схеме (прямые запросы к API, загрузка в свою staging-папку)
  он неприменим. Значение имеет только свободное место там, где лежит
  `data_dir`: на 13.09.2026 это D: с 24,4 ГБ при потолке папки 4 ГБ.
- **Сироты от разовых чисток.** `cleanup_blue_detections.py` убрал из отчётов
  412 920 синих детекций, но файлы намеренно оставил («дешевле места, чем
  риск удалить нужное»). Через год это 2,81 ГБ мусора. Убрано скриптом
  `prune_crops.py`. **Урок: разовый скрипт, оставляющий файлы, обязан
  оставлять и способ их убрать** — иначе долг не вернут никогда.
- **Кроп пишется на каждую детекцию, а в отчёт попадает не больше 80 на
  сцену.** Остальное — мёртвый груз (медиана сцены 9 детекций, 90-й
  процентиль 121, максимум 1598). `prune_unshown_crops()` в детекторе
  убирает лишнее после группировки, порог по умолчанию равен тому, что и так
  встраивается в HTML, — то есть видимое поведение не меняется.

- **Проверка баланса скобок в шаблоне ненадёжна для карточки операции.**
  Упрощённый разбор строк спотыкается о регулярку `/[&<>"']/g` в `esc()`:
  кавычка внутри неё принимается за начало строки, и счёт разъезжается ещё
  до конца шапки. Такой тест давал бы ложный сигнал, и его там намеренно
  нет -- синтаксис проверяется загрузкой страницы в браузере. Для админки
  (где такой регулярки нет) проверка работает и оставлена.

### Грабли фронтенда плеера

- **Полноэкранный режим нельзя перезапросить после `await exitFullscreen()`** —
  разрешение на переход требует «свежего» пользовательского действия, а оно к
  этому моменту истекает. Собственная кнопка полноэкранного режима в итоге
  **убрана осознанно**: остались двойной клик и штатное меню «три точки».
- **Определение «человек сейчас печатает» должно смотреть на тип поля.**
  Проверка «это `<input>`?» ломала все горячие клавиши, стоило чекбоксу
  «оригинал» получить фокус.
- **Боксы разметки — в SVG с `vector-effect: non-scaling-stroke`**, иначе при
  зуме рамка выглядит рвано.
- **Переход на таймкод**: сначала пауза, затем перемотка, и рисовать бокс по
  событию `seeked` — иначе бокс отрисуется по старому кадру.

### Про тесты

- **Тест, который проходит только в общем прогоне, — сломанный тест.** Один
  тест дашборда опирался на счётчики, заполненные предыдущими файлами, и падал
  в одиночку. Прогоняй подозрительный тест отдельно.
- **Тест не должен зависеть от свободного места на машине.** Проверки
  временной папки пишут НАСТОЯЩИЕ файлы по десяткам мегабайт. Когда на C:
  осталось 1,1 ГБ, девять тестов покраснели разом, а потом прогон рассыпался
  с `database or disk is full` — при том, что проверяемый код не менялся.
  Диск фиксируется общей фикстурой в `tests/conftest.py`.
- **`tmp_path_retention_policy = failed` и `--basetemp` ЛОМАЮТ набор.** Оба
  соблазнительны (места на C: мало), оба молча роняют посторонний тест.
  pytest режет имя теста до 30 символов, и папки начинают совпадать:
  `test_tree_returns_coverage_for_queued_video` и
  `..._for_processing_video` дают одно имя. Общая папка = общий `watch_dir`,
  а он входит в ключ кеша `/api/tree` — второй тест получает ответ,
  посчитанный для первого. Проверено обоими способами, причина записана в
  `pytest.ini`.
- **Мутационная проверка сама может врать.** Дважды 17.09.2026 мутация
  «не поймана» оказалась просто не применённой: обратные слэши в строке
  замены схлопывались при передаче скрипта в оболочку, а `rindex` нашёл
  похожую строку в ЧУЖОЙ функции и вырезал условие оттуда. Всегда печатай
  «подстрока найдена / файл изменён» и что именно вырезано — иначе зелёный
  прогон под мутацией читается как слабый тест, хотя тест хороший.
- **Не зашивай в тест текущее время или имя файла с датой** — такой тест
  «протухает» через час.
- **Измеряя качество кодирования, не ставь `-ss` перед `-i`** — перемотка
  прыгает на опорный кадр, и сравниваются разные кадры. Ошибка вскрылась
  ровно потому, что все значения CRF дали одинаковый результат.

      молча. Не подтверждён — НИЧЕГО не трогаем: неизвестность не равна
      изменению (тот же принцип, что `probe()` у сторожа туннеля).
    - **`myipv6=preserve` обязателен** — без него обновление по IPv4
      стирает запись AAAA, тихо.
    - **Имя живёт только в `sar_config.json`**, в Caddyfile подставляется
      из него. Второе место завело бы два источника правды — как с папкой
      резервных копий, которая считалась трижды и дважды неверно.
    - **Сжимается только текст.** Гонять видео через gzip — потратить
      процессор, нужный ffmpeg, и не выиграть ничего. Проверено на живой
      цепочке: страница 28 КБ → 9 КБ, видео 206 и без сжатия.
    - **В Caddyfile НЕТ глобального блока с `email`** — Caddy не принимает
      пустое значение и отказывается разбирать конфиг целиком, то есть
      незаполненное необязательное поле роняло бы запуск.
    - **Режим `local` идёт по http на 8081, а не по https://localhost** —
      для localhost Caddy лезет ставить корневой сертификат в хранилище
      Windows, это запрос прав, и в фоне запуск встаёт намертво.

    **Хорошая новость про переезд:** в `sar_server.py` НОЛЬ абсолютных
    ссылок (`_external=True`) — поэтому он и пережил вечно меняющийся
    адрес туннеля, и за обратным прокси чинить нечего.

    Побочно закрывается давняя подпорка: постоянные ссылки на находки
    идут через бота именно потому, что адрес туннеля протухал. С
    постоянным именем это больше не нужно.
12. **Хранение истории присутствия** — сейчас видно только «сколько сейчас»,
    восстановить пик задним числом нельзя.
13. **GPU-инференс** — единственный рычаг на порядок, если пропускная
    способность станет узким местом.
14. **Checkpoint/resume для воркера** — прерванное видео пересчитывается с нуля.
15. **Карта GPS-координат находок** — выгрузка в KML/GPX уже есть (фича 20),

## Как запускать

```powershell
# один раз
copy sar_config.example.json sar_config.json
# отредактировать sar_config.json: shared_password, model, model_type, classes

# каждый раз, в разных окнах
python sar_worker.py        # обработка
python sar_server.py        # веб
python sar_telegram_bot.py  # бот (нужен токен в sar_config.json)

# мониторинг (опционально)
cd monitoring; docker compose up -d
```

Наружу платформа смотрит через туннель. **Туннель — известная слабая точка:**
он умирал трижды, и мониторинг этого не видел (см. приоритет 8).

CLI без сервера тоже доступен: `sar_video_review.py --video ... --out ...`,
аналогично `sar_photo_review.py`, либо пакетно через `sar_batch.py`.

## Стиль работы, которого стоит держаться

- **Секреты.** `sar_config.json` содержит общий пароль, токен бота и
  chat_id — он **никогда** не коммитится и не попадает в архив обновлений.
  В комплекте только `sar_config.example.json`.
- **Рассылки.** Ничего не рассылать пользователям бота по своей инициативе.
  Новая ссылка выдаётся в ответ на `/help`, а не рассылкой.
- Любое изменение — сразу проверять реальным тестом (Flask test client,
  прямой вызов функции, `node --check` для JS), а не полагаться на "должно
  сработать". В этом проекте уже несколько раз именно тесты ловили баги,
  которые не были очевидны по коду.
- Если тест сам оказался нерепрезентативным (ложный позитив/негатив) —
  честно это признавать и переделывать тест, а не просто менять код под
  прошедший тест.
- Изменения в `sar_video_review.py`/`sar_photo_review.py` (детектор) не
  требуют перезапуска `sar_worker.py` — он запускает их отдельным
  процессом на каждое новое видео и подхватывает актуальный код сам.
  Изменения в `sar_worker.py`/`sar_common.py`/`sar_server.py` требуют
  перезапуска соответствующего процесса.
- При урезании/переносе кода между файлами — обязательно перепроверять
  импорты (см. грабли про `import time` выше).
