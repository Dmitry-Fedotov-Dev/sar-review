# SAR Review — поиск людей и снаряжения на видео с дрона

Self-hosted веб-сервис для поисково-спасательных работ: просматривает видео и
фото с дрона, подсвечивает кадры, где вероятно есть человек или снаряжение, и
помогает команде разобрать отснятый материал, не пересматривая часы записи
вручную.

**Разработан во время реальной поисково-спасательной операции** — поиск
пропавших альпинистов в Алайском районе Кыргызстана, у пика Корумду. Не
учебный проект: им пользовались в поле, поэтому в коде много решений,
продиктованных конкретными проблемами, всплывшими на месте (см. раздел
«грабли» в [CLAUDE.md](CLAUDE.md)).

> **Это инструмент приоритизации внимания человека, а не замена наземным
> группам, повторным облётам и стандартным протоколам поиска.** Все
> координаты объектов — расчётная оценка с реальной погрешностью, а не
> измерение. Прочитайте раздел про координаты перед тем, как отправлять
> кого-то по этим цифрам.

## Что умеет

- **Мультикласс-детекция** (YOLO-World без дообучения или своя модель) с
  тайлингом кадра — плюс отдельный детектор цветовых аномалий для одежды и
  снаряжения, которое object detection на мелком масштабе часто пропускает.
- **Группировка тысяч детекций в «сцены»** — иначе отчёт нерабочий на
  реальном масштабе.
- **Оценка координат объекта** по GPS, высоте и углам подвеса, с учётом
  фактического зума кадра. Отдельно показываются точные координаты дрона.
- **Ручной плеер** с разметкой находок мышью/пальцем, привязкой к таймкоду,
  GPS и общей для команды полосой покрытия «что уже реально просмотрено».
- **Триаж находок** (точно человек / предположительно / предмет / отклонено)
  — статус ставит только человек, система никогда не проставляет его сама.
- **Экспорт датасета** (YOLO) из подтверждённых находок для дообучения.
- **Работает без интернета** — полностью локальный сервис в сети операции.
- Опциональный **Telegram-бот** для выдачи доступа волонтёрам с одобрением
  координатора.

## Требования

Python 3.10+, ~4 ГБ свободной памяти для инференса на CPU. GPU не обязателен,
но заметно ускоряет обработку. Проверялось на Windows 11 и Python 3.13.

Веса модели в репозиторий не входят — `ultralytics` скачает их при первом
запуске, либо положите свой `.pt` рядом и укажите путь в конфиге.

## ⚠️ Если вы уже разворачивали проект и обновляете файлы

**Не распаковывайте архив в папку проекта "с заменой всех файлов" бездумно.**
`sar_config.json` в этом архиве больше не поставляется напрямую — вместо
него теперь идёт `sar_config.example.json` (шаблон), именно чтобы очередная
распаковка не затирала ваш реальный пароль и настройки модели обратно на
дефолтные. При обновлении файлов проекта на новую версию:

- **можно перезаписывать:** `sar_server.py`, `sar_video_review.py`,
  `sar_photo_review.py`, `sar_batch.py`, `requirements.txt`, `README.md`
- **НЕ перезаписывайте:** свой `sar_config.json` (если он уже создан и
  настроен) — просто не давайте архиватору его тронуть, либо распаковывайте
  во временную папку и переносите файлы вручную, кроме конфига.
- `sar_config.example.json` из архива можно перезаписывать всегда — это
  просто шаблон, не тот файл, который читает сервер.

Если вы уже успели несколько раз распаковать поверх и подозреваете, что
пароль в `sar_config.json` мог откатиться на `change_me` — откройте файл и
проверьте `"server": {"shared_password": ...}` прямо сейчас.

## Быстрый старт (веб-сервис, self-hosted, многопользовательский)

**С этой версии нужны ДВА процесса одновременно** — обработка вынесена из
веб-сервера в отдельный `sar_worker.py`, именно чтобы перезапуск/обновление
веб-интерфейса не прерывало текущую обработку видео. Оба запускаются из
одной и той же папки, читают один и тот же `sar_config.json`.

1. Положите все файлы из этого архива в папку, где лежат (или будут появляться)
   видео и фото с дрона — эта папка станет `watch_dir`.
2. Установите зависимости:
   ```
   pip install -r requirements.txt
   ```
   (на Windows иногда нужно `python -m pip install -r requirements.txt`)
3. **Один раз** скопируйте шаблон в рабочий конфиг:
   ```
   copy sar_config.example.json sar_config.json
   ```
   (на Linux/Mac: `cp sar_config.example.json sar_config.json`)

   Дальше редактируете только `sar_config.json` — `sar_config.example.json`
   не трогаете, это просто эталон на случай, если захотите свериться с
   дефолтами или начать настройку заново.
4. Откройте `sar_config.json`, смените:
   - `"shared_password"` — на реальный пароль для входа
   - `"model"` / `"model_type"` / `"classes"` — под вашу задачу
5. Запустите **оба** процесса, каждый в своём окне консоли:
   ```
   python sar_worker.py
   ```
   ```
   python sar_server.py
   ```
   Порядок запуска не важен — какой бы ни стартовал первым, он сам создаст
   недостающие служебные файлы (БД, папку `sar_data/`).
6. Откройте `http://<адрес_сервера>:8080` в браузере, войдите (пароль + любое имя).

Видео/фото, которые вы кладёте **прямо в корень** этой папки (без подпапок —
подпапки сознательно не сканируются, см. ниже), автоматически встают в очередь
и обрабатываются в фоне процессом `sar_worker.py`. На странице файла — живой
вывод консоли и прогресс, пока идёт обработка; после готовности — интерфейс
сцен с зумом, рамками, GPS-координатами и статистикой просмотров, плюс
отдельный ручной плеер с разметкой и наблюдениями.

### Загрузка видео и телеметрии через браузер

Кроме ручного копирования файлов в папку, на странице списка файлов есть две
кнопки — "📤 Загрузить видео" и "📤 Загрузить телеметрию (SRT)" (вторая
принимает сразу несколько файлов за раз — реальная телеметрия обычно
приходит целой пачкой с одного дня полётов). Обе видны и работают **только**
для того, кто вошёл под именем `uploader` (регистрозависимо, ровно так). Это
временный барьер "от случайности", **не настоящая авторизация**: в системе
нет ролей и аккаунтов вообще (один общий пароль на всех + любое имя при
входе), поэтому любой, кто знает общий пароль, может ввести имя `uploader` и
получить доступ к загрузке — так же, как и к чему угодно ещё в системе.
Ограничение сделано осознанно как временное решение, до нормальной ролевой
модели.

Загруженная телеметрия сразу становится доступна для поиска (индекс
`telemetry/` перестраивается на лету, без рестарта сервера) — но это влияет
только на видео, которые будут обработаны ПОСЛЕ загрузки. Уже готовые
отчёты не подтягивают новую телеметрию автоматически — для них нужно
отдельно запустить `python backfill_telemetry.py`.

### Telegram-бот для выдачи доступа волонтёрам — `sar_telegram_bot.py`

Отдельный, третий независимый процесс (как и `sar_worker.py`/`sar_server.py`,
общается с ними только через `sar_data.db`, ничего не запускает и не
обрабатывает сам). Решает конкретную проблему: не палить пароль и ссылку на
сервис в открытых постах/сторис, а выдавать доступ только тем, кого
координатор реально одобрил.

Поток: человек пишет боту `/start` → координатору(ам) приходит заявка с
кнопками "✅ Одобрить"/"❌ Отклонить" → **только после одобрения** бот сам
присылает человеку ссылку на сервис, пароль, ссылку на гайд волонтёра и на
презентацию. До одобрения — никакой конкретики, только "заявка отправлена".
Повторный `/start` от уже одобренного/отклонённого не меняет решение и не
спамит координаторов заново.

Настройка — секция `"telegram_bot"` в `sar_config.json`:

```json
"telegram_bot": {
  "bot_token": "...",           // получить у @BotFather в Telegram
  "admin_chat_ids": [123456789], // ваш числовой chat_id (например, через @userinfobot)
  "service_url": "https://....trycloudflare.com",
  "guide_url": "https://claude.ai/code/artifact/...",
  "presentation_url": "https://claude.ai/code/artifact/..."
}
```

Пароль отдельно не хранится — берётся из `server.shared_password`, чтобы не
было двух источников правды. Запуск: `python sar_telegram_bot.py` (нужен
`python-telegram-bot`, см. `requirements.txt`). Команда `/pending` у
координатора — список заявок в ожидании (на случай, если пропустил
уведомление).

### Телеметрия (GPS/высота/углы подвеса) — папка `telemetry/`

SRT-телеметрия ищется в двух местах, по порядку:

1. **Рядом с самим видео**, то же имя + `.srt` (например `DJI_0001.MP4` +
   `DJI_0001.srt`) — как и раньше, самый однозначный вариант.
2. Если такого файла нет — **рекурсивно внутри папки `telemetry/`** (рядом с
   видео, создаётся автоматически при старте). Туда можно класть SRT как
   есть, россыпью или целыми папками экспорта с полёта (например
   `telemetry/12.08.2026 Субтитры полетов/DJI_0001.SRT`) — подпапки внутри
   `telemetry/` сканируются рекурсивно (в отличие от самой `watch_dir`).
   Сначала ищется точное совпадение имени файла; если имена не совпадают —
   резервный поиск по метке времени, встроенной в стандартное имя файла DJI
   (`DJI_YYYYMMDDHHMMSS_...`), но только если расхождение не больше 5 минут
   — на большем расхождении система не гадает и оставляет видео без GPS
   (это лучше, чем подставить координаты от другого вылета).

Если телеметрия нашлась, GPS/высота (относительная и абсолютная) и (если
прошивка их пишет) углы подвеса yaw/pitch/roll попадают в `detections.json`,
`detections.csv` и в карточки сцен отчёта — с прямой ссылкой "🗺 карта" на
Google Maps рядом с координатами (в отчёте и в ручном плеере).

### Триаж детекций (ранжирование) — плеер

У каждой детекции (и модели, и ручной) в плеере есть выпадающий список
статуса: **✅ точно человек · 👤 предположительно человек · 🎒 предмет ·
🎒 предположительно предмет · ❌ отклонено** (плюс "не размечено" по
умолчанию). Ставит статус **только человек** — сервер никогда не проставляет
его сам, ни во время обработки, ни при бэкфилле; это осознанное ограничение,
особенно важное для "✅ точно человек".

Статусы хранятся в таблице `detection_priorities`, отдельно от
`detections.json`/`report.html` — переобработка видео их не стирает. Для
AI-сцен статус привязан не к позиционному `group_id` (он меняется при
переобработке), а к отпечатку содержимого сцены (класс + источник + первый
кадр). На главной странице — счётчики "🤖 детекций модели · ✍️ ручных" по
каждому файлу и сортировка по их сумме.

### Экспорт датасета для дообучения — `sar_dataset_export.py`

Отдельный CLI-скрипт (как `sar_batch.py`/`backfill_telemetry.py`), собирает
из накопленного триажа (см. выше) датасет формата YOLO для дообучения
детектора конкретно под горную местность:

```
python sar_dataset_export.py --out sar_dataset
python sar_dataset_export.py --out sar_dataset --val-split 0.15
python sar_dataset_export.py --out sar_dataset --report-id <id>
```

Экспортируются только **проверенные человеком** детекции —
`confirmed_person`/`confirmed_object` (позитив, 2 класса — `person`/`object`,
без более мелкой неверифицированной догадки модели про конкретный тип) и
`rejected` (тот же полный кадр, но БЕЗ рамки — хардовый негатив: учит модель
не путать этот конкретный паттерн, обычно источник ложных срабатываний, с
целью). `likely_*` и непроверенные детекции сознательно исключены.

Train/val-сплит детерминирован по хэшу — одна и та же картинка всегда
попадает в один и тот же сплит между запусками, иначе метрики валидации
были бы не сопоставимы от прогона к прогону. Каждый запуск пересобирает
`images/`/`labels/` с нуля из текущего состояния триажа — "постоянное
обновление" датасета означает повторные запуски по мере роста триажа, а не
потоковую запись в реальном времени. Данные это реальные кадры действующей
поисковой операции — датасет предназначен для использования только внутри
команды/МЧС.

### Координаты дрона vs. вероятные координаты объекта

**Важно понимать разницу** — в отчёте и плеере теперь показываются ДВЕ разные
пары координат:

- **📍 координаты дрона** — то, что реально пишет SRT-телеметрия: GPS самого
  летательного аппарата в момент кадра. Точные (в пределах точности GPS
  дрона), но это НЕ место, где находится обнаруженный человек/объект — на
  высоте и под углом обзора камеры (а в реальных полётах здесь высота может
  быть 1000+ м, угол подвеса — почти горизонтальный) объект в кадре может
  быть в сотнях метров от точки прямо под дроном.
- **🎯 вероятные координаты объекта** — геометрическая ОЦЕНКА (высота + угол
  подвеса + положение рамки детекции в кадре + угол обзора кадра), не
  измерение. Реальная погрешность складывается из нескольких источников:
  - **зум УЧИТЫВАЕТСЯ** — FOV считается для каждого кадра из его `focal_len`
    (SRT) и размеров матрицы (`camera_sensor_width_mm`/`_height_mm`,
    `focal_len_scale` в конфиге). Дефолты — под **DJI M30T, zoom-камера**
    (файлы с суффиксом `_Z`): матрица 1/2" 6.4×4.8 мм, `focal_len` в SRT в
    десятых долях мм. **Другая камера — обязательно поменяйте**, иначе все
    оценки будут систематически смещены. Аварийный выключатель —
    `use_focal_len_fov: false` (вернётся старое поведение с фиксированным
    `camera_hfov_deg`, он же используется, если в SRT нет `focal_len`);
  - **рельеф НЕ учитывается** — предполагается ровная земля на высоте точки
    взлёта дрона. В горах это главный источник погрешности: ошибка ≈
    Δh·tan(угол от надира), т.е. при перепаде 100 м и типичном угле это
    ~240 м, а на пологих углах (съёмка почти вдоль склона) — километры;
  - ошибка угла подвеса в 1° даёт от ~45 м (крутой угол) до ~900 м
    (пологий).

  Порядок величин на реальных данных этой операции (высота ~1150 м):
  **сотни метров при съёмке вниз, километры при съёмке почти вдоль
  горизонта.** Это ориентир «куда посмотреть», а не геодезическая привязка.

  Если камера смотрит на/выше горизонта — оценка не считается вообще (лучше
  никакой оценки, чем заведомо неверная).

Обе пары координат — со своей ссылкой "🗺 карта" — есть и в автоматическом
отчёте (карточка сцены + полноэкранный просмотр кадра), и в ручном плеере
(список "Сцены (модель)" справа).

### Опциональный бэкенд тайлинга — SAHI

По умолчанию используется собственная нарезка кадра на тайлы + NMS
(`detect_frame_tiled`/`make_tiles`/`nms` в `sar_video_review.py`) — то, что
проверено на боевых данных. Есть опциональный альтернативный бэкенд через
библиотеку [SAHI](https://github.com/obss/sahi) (`detect_frame_sahi`),
**выключенный по умолчанию** и никак не влияющий на поведение, если его не
включать:

```
pip install -r requirements-sahi.txt
```
```json
"detector_backend": "sahi"
```
в `sar_config.json` (или `--detector-backend sahi` в CLI). Это отдельная,
пока не обкатанная на реальных полётах ветка — переключайте осознанно.

### Что даёт разделение на два процесса

- **`sar_server.py` можно свободно останавливать/обновлять/перезапускать в
  любой момент** — текущая обработка видео в `sar_worker.py` при этом
  НЕ прерывается и НЕ теряет прогресс. Веб-интерфейс просто на несколько
  секунд перестаёт отвечать, а после перезапуска сразу видит актуальное
  состояние (оно всё это время писалось в общую БД).
- **`sar_worker.py` тоже можно перезапускать** (например, чтобы обновить
  его код) — очередь и уже готовые результаты не теряются. Но: если в
  момент остановки воркера какое-то видео как раз обрабатывалось —
  досчитать "с того места" нельзя (детектор не поддерживает докачку
  с середины), при следующем запуске оно просто начнёт считаться заново
  с нуля. Это не потеря данных, а пересчёт — просто дольше.

## Файлы в архиве

| Файл | Назначение |
|---|---|
| `sar_server.py` | Веб-интерфейс: файловый браузер, авторизация, отдача страниц, статистика, индикатор "онлайн", ручной плеер. Не запускает обработку сам. |
| `sar_worker.py` | Фоновая обработка: следит за папкой, ставит новые файлы в очередь, запускает детектор. Отдельный процесс, не зависит от sar_server.py. |
| `sar_common.py` | Общий код между sar_server.py и sar_worker.py (конфиг, БД, сканирование папки) |
| `sar_video_review.py` | Детектор для видео (тайлинг, группировка в сцены, отчёт) — использует sar_worker.py, и его можно запускать отдельно как CLI |
| `sar_photo_review.py` | То же самое для одиночных фото |
| `sar_batch.py` | Отдельный CLI-инструмент для очереди/пакетной обработки папки с видео БЕЗ веб-сервиса (если веб-сервис не нужен, а нужна просто очередь на одной машине) |
| `sar_config.example.json` | Шаблон настроек — скопируйте в `sar_config.json` один раз, дальше редактируйте только копию |
| `requirements.txt` | Python-зависимости |

## Важно перед хостингом наружу (за пределами локальной сети/VPN)

- Пароль передаётся без HTTPS — для реального внешнего доступа нужен
  обратный прокси (nginx/Caddy) с HTTPS перед Flask. Для использования
  только в локальной сети/VPN операции это принятый риск.
- `sar_server.py` теперь запускается через `waitress` (production WSGI,
  чистый Python, работает на Windows) автоматически, если он установлен
  (`pip install -r requirements.txt` ставит его сам). Если `waitress` не
  найден — сервер сам сообщит об этом в консоли и упадёт обратно на
  dev-сервер Flask (тот, что был раньше) — работает, но не для боевой
  постоянной нагрузки.
- Для постоянной работы на "боевом" хосте стоит завернуть **оба** процесса
  (`sar_server.py` и `sar_worker.py`) в отдельные systemd-сервисы (Linux) или
  задачи планировщика/NSSM (Windows) с автоперезапуском — именно раздельные,
  чтобы сохранить главное преимущество разделения (обновление одного не
  трогает другой).
- Подпапки в `watch_dir` **не сканируются намеренно** (защита от рекурсивной
  обработки собственных же результатов) — все видео/фото, которые нужно
  обработать, должны лежать прямо в корне.

## CLI-режим без сервера (на будущее / для разовой обработки)

```
python sar_video_review.py --video video.mp4 --model yolov8s-worldv2.pt \
    --model-type yolo-world --classes "person,tent" --out ./review_video1

python sar_photo_review.py --photo photo1.jpg --model yolov8s-worldv2.pt \
    --model-type yolo-world --classes "person,tent" --out ./review_photo1

python sar_batch.py --input-dir ./videos --out-root ./review_all \
    --model yolov8s-worldv2.pt --model-type yolo-world --classes "person" --workers 1
```

Все три режима (CLI, `sar_server.py`, `sar_worker.py`) используют один и тот
же `sar_config.json` (не `sar_config.example.json`).
